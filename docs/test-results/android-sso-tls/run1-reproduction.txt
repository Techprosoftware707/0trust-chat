Android sign-in on Android 9: reproduction (CI run 1, before the fix)
=====================================================================
GitHub Actions run 39078879876 (workflow_dispatch, android.yml), commit 6f198ee, 2026-10-17
https://github.com/Techprosoftware707/0trust-chat/actions/runs/39078879876
Code as the phone had it (no change to the certificate verifier's decision); this commit only added
diagnostics (TlsDiagnostics, sign-in error Details) and the tests below. Emulators: google_apis
x86_64, API 26 / 28 / 35. Excerpts copied from the job logs (timestamps removed).

Report: a debug build on an Android 9 phone discovers the user's server (DuckDNS name, Let's
Encrypt certificate, Caddy) and then shows "We couldn't start sign-in with this server"
(SignInError.SSO_START_FAILED): AuthController.startSso -> SessionManager.startSso threw before
Custom Tabs opened.

Finding: on every Android version tested (8.0, 9, 15), the Rust SDK's certificate verifier refuses
public certificates that name no OCSP responder and only a CRL. Let's Encrypt's current
certificates (Gen Y chain YR1 <- Root YR) and matrix.org's (Google Trust Services WE1) are such
certificates. The verifier reports them as Revoked with
  java.security.cert.CertPathValidatorException: Certificate does not specify OCSP responder
and the SDK turns that into ClientBuildException.ServerUnreachable "error sending request" while
building the sign-in client: exactly SSO_START_FAILED. Discovery works because it uses the platform
HTTP client, which does not check revocation. The CRL host (yr1.c.lencr.org) is blocked for plain
http by the app's network security config, so the CRL fallback cannot help either.

Not Android-9-specific: API 35 fails identically. The earlier API 35 end-to-end test signed in
because its server uses a private test CA, for which the verifier skips revocation entirely.
On Android 9 with that private CA, startSso itself works (Keystore, encrypted stores, SDK client,
/versions, startSsoLogin): see the API 28 e2e excerpt below.
